# Trazabilidad del modelo de datos

Esta matriz relaciona la primera implementación del dominio con los requerimientos funcionales y no funcionales del documento del proyecto.

| Requisito | Entidades principales                      | Cobertura del modelo                                                                                                                                         |
| --------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| RF-01     | `usuario`, `rol`, `auditoria`              | Cuenta activa, hash PBKDF2, sesión cifrada, validación de vigencia y auditoría de accesos.                                                                   |
| RF-02     | `usuario`, `rol`, `auditoria`              | API administrativa para crear, consultar, modificar, activar y desactivar cuentas y asignar roles.                                                           |
| RF-03     | `dispositivo`, `auditoria`                 | API y cliente para consultar, registrar y editar nombre, host, tipo, modelo, protocolo, puerto y fuente; autorización y estados bajo control administrativo. |
| RF-04     | `dispositivo`, `captura`, `version_config` | Carga de archivos y capturas SSH o NETCONF reales de solo lectura, con validación de identidad, límite temporal y saneamiento previo a la persistencia.      |
| RF-05     | `evento_cambio`, `captura`, `version_config` | Receptor Syslog configurable: valida el origen, sanea y deduplica; la captura remota solo crea versión cuando cambia la huella de configuración.            |
| RF-06     | `version_config`, `captura`, `dispositivo` | Contenido local o remoto normalizado, número consecutivo, origen, fecha, comentario, contenido preservado y huella SHA-256 implementados.                    |
| RF-07     | `version_config`                           | API y cliente de historial con filtro por dispositivo; contrato adicional por fecha, origen y estado, respaldado por índices.                                |
| RF-08     | `comparacion`, `detalle_diferencia`        | API y cliente para comparar versiones del mismo dispositivo, clasificar cambios por línea, conservar resultados y consultar su historial.                    |
| RF-09     | `baseline`, `regla_baseline`               | API y cliente administrativos para crear criterios inmutables por dispositivo o tipo, consultar el catálogo y controlar su vigencia.                         |
| RF-10     | `verificacion`, `resultado_regla`          | API y cliente para evaluar versiones compatibles, calcular el resultado general, conservar evidencia por regla y consultar el historial.                     |
| RF-11     | `version_config`, `usuario`                | Una versión histórica compatible puede asociarse como referencia opcional y queda marcada estable con usuario y fecha de validación.                         |
| RF-12     | `auditoria`                                | Registro transversal y consulta administrativa paginada por usuario, acción, entidad, estado y rango de fechas, sin contenido sensible.                    |
| RF-13     | Entidades de resultados                    | Resultados independientes del contenido original.                                                                                                            |

| Requisito no funcional | Decisión aplicada                                                                                                                                          |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RNF-01                 | Cookie cifrada, autorización por roles, sesión limitada y revocación al desactivar usuario o rol.                                                          |
| RNF-02                 | Hash PBKDF2 para cuentas; Data Protection y contratos sin exposición para secretos de equipos; cookies `HttpOnly`, CSRF, CORS exacto y límite de intentos. |
| RNF-03                 | Huellas SHA-256 sobre contenido canónico, versiones consecutivas, claves foráneas, índices únicos y metadatos UTC.                                         |
| RNF-04                 | Entidad de auditoría y referencias persistentes entre operaciones y resultados.                                                                            |
| RNF-05                 | Índices en fechas, estados y claves utilizadas por historial y resultados.                                                                                 |
| RNF-08                 | Dominio sin dependencia de EF Core y configuraciones aisladas en Infraestructura.                                                                          |
| RNF-10                 | Tipo, fuente, huella SHA-256, estado, dispositivo, captura y versión asociada para cada evento Syslog aceptado.                                             |

Las pruebas de dominio, aplicación e integración verifican la normalización de cuentas y hosts, la protección de contraseñas y secretos, la invalidación de confianza al cambiar un punto de conexión, el rechazo CSRF, la sesión, los roles, los canales admitidos, la consulta paginada de auditoría sin secretos, las restricciones administrativas, el enmascaramiento exigido en archivos, el saneamiento automático de respuestas remotas, la preservación de versiones sucesivas, la comparación exclusiva de versiones del mismo dispositivo y la compatibilidad entre una línea base y su versión evaluada. Los conectores simulados comprueban la orquestación de SSH o NETCONF sin contactar la red; pruebas puras adicionales verifican el algoritmo y la huella exigidos antes de autenticar, el RPC NETCONF fijo de solo lectura, el rechazo de `<rpc-error>`, el saneamiento XML, la clasificación de líneas agregadas, eliminadas y modificadas, y los criterios `Contiene`, `NoContiene` y `CoincideExpresionRegular`. Las pruebas del cliente verifican capturas SSH y NETCONF, la comparación diferencial, la ejecución y presentación de verificaciones, la bitácora reservada al administrador, que el técnico pueda operar evidencia sin recibir controles administrativos, y que la administración del acceso no muestre ni conserve el secreto enviado.
